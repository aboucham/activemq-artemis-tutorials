= Step-by-Step Tutorial: Filtering AMQ Broker Metrics using JMX Exporter on OpenShift

This tutorial provides a step-by-step guide to configuring a highly customized metrics architecture for *Red Hat AMQ Broker on OpenShift Container Platform*.

By default, the AMQ Broker Operator provides an internal Prometheus plugin that exports a wide baseline of metrics. However, to dramatically reduce metrics noise and storage footprints, this tutorial demonstrates how to leverage an *Init Container strategic patch* to inject the *Prometheus JMX Exporter Java Agent* into your broker pods, allowing you to precisely whitelist only your high-value metrics targets (such as address sizes and consumer counts).

== Prerequisites

* A running OpenShift Container Platform (OCP) cluster.
* The AMQ Broker Operator deployed in your namespace.
* Cluster administrator privileges or standard deployment privileges in the designated project.
* A local workspace configured with the `oc` command-line interface (CLI).

== Step 1: Define the JMX Exporter Filtering Rules

The Prometheus JMX Exporter allows you to match specific Java Management Extensions (JMX) MBeans and filter out unlisted patterns. We will craft a configuration that exposes *exclusively* your chosen address size and consumer count metrics, leaving behind the remainder of the noise.

Create a local file named `jmx-rules.yaml` containing the configuration below:

[source,yaml]
----
lowercaseOutputName: true
lowercaseOutputLabelNames: true

# Restrict the JMX Agent scanner to the ActiveMQ domain MBeans exclusively
includeObjectNames: ["org.apache.activemq.artemis:*"]

rules:
  # Rule 1: Match Address Size (Gauge)
  - pattern: 'org.apache.activemq.artemis<broker=".*", component=addresses, address="(.*)"><>AddressSize'
    name: artemis_address_size
    type: GAUGE

  # Rule 2: Match Queue Consumer Count (Gauge)
  - pattern: 'org.apache.activemq.artemis<broker=".*", component=addresses, address=".*", subcomponent=queues, routing-type=".*", queue="(.*)"><>ConsumerCount'
    name: artemis_consumer_count
    type: GAUGE

  # Rule 3: Match Queue Delivering Durable Message Count (Gauge)
  - pattern: 'org.apache.activemq.artemis<broker=".*", component=addresses, address=".*", subcomponent=queues, routing-type=".*", queue="(.*)"><>DeliveringDurableMessageCount'
    name: artemis_delivering_durable_message_count
    type: GAUGE
----

== Step 2: Encapsulate the Rules into an OpenShift Secret

To securely pass this customized filtration schema down into your dynamic broker runtime pods, convert the local file into a generic OpenShift secret asset.

Execute the following command in your terminal:

[source,bash]
----
$ oc create secret generic jmx-metrics-config --from-file=config.yaml=jmx-rules.yaml
----

== Step 3: Author and Deploy the ActiveMQArtemis Custom Resource

We will now modify the core `ActiveMQArtemis` Custom Resource (CR) instance to drive the automated injection pipeline. 

This manifest performs three key operations:

1. *Mounts the Secret File:* Uses `extraMounts` to attach the JMX rules file to the pod file system.
2. *Declares an Init Container Strategic Patch:* Patches the underlying `StatefulSet` via `resourceTemplates` to automatically download the standard `1.5.0` JMX Prometheus Exporter JAR during pod generation.
3. *Appends Java Boot Flags:* Uses the `JAVA_ARGS_APPEND` environment variable to link the agent to the main JVM executable launch command.

Create a deployment manifest file named `broker-deployment.yaml`:

[source,yaml]
----
apiVersion: broker.amq.io/v1beta1
kind: ActiveMQArtemis
metadata:
  name: broker-prod
  namespace: amq
spec:
  adminUser: admin
  adminPassword: admin
  version: "7.13" # Match your installed broker minor channel baseline
  
  acceptors:
    - expose: true
      name: amqp
      port: 5672
      protocols: amqp
      sslEnabled: false

  console:
    expose: true # Exposes the standard management portal endpoint

  env:
    # Wire the JMX Prometheus Java agent smoothly onto the system JVM bootloader path
    - name: JAVA_ARGS_APPEND
      value: '-javaagent:/amq/init/config/extra-libs/jmx_prometheus_javaagent.jar=9404:/amq/extra/secrets/jmx-metrics-config/config.yaml'

  deploymentPlan:
    size: 1
    persistenceEnabled: true
    journalType: aio
    requireLogin: false
    clustered: false
    extraMounts:
      secrets:
        - jmx-metrics-config # Binds our secret to /amq/extra/secrets/jmx-metrics-config/

  brokerProperties:
    # Opt-out of standard metrics noise via underlying core settings properties
    - addressSettings.#.enableMetrics=false
    - addressSettings.samplequeue.enableMetrics=true

  resourceTemplates:
    - selector:
        kind: StatefulSet
      patch:
        kind: StatefulSet
        spec:
          template:
            spec:
              initContainers:
                # Automate the runtime delivery of the missing metrics Java agent binaries
                - name: jmx-exporter-agent-init
                  image: 'registry.redhat.io/amq7/amq-broker-rhel8:7.12'
                  volumeMounts:
                    - mountPath: /amq/init/config
                      name: amq-cfg-dir
                  command:
                    - bash
                    - '-c'
                    - 'mkdir -p /amq/init/config/extra-libs && curl -Lo /amq/init/config/extra-libs/jmx_prometheus_javaagent.jar https://github.com/prometheus/jmx_exporter/releases/download/1.5.0/jmx_prometheus_javaagent-1.5.0.jar'
----

Apply this Custom Resource manifest to your active namespace:

[source,bash]
----
$ oc apply -f broker-deployment.yaml
----

== Step 4: Verify the Process Runtime Infrastructure

Once the pods transition to a running state, verify that the Java execution command properly contains your agent and config file paths.

Access a remote terminal shell on your running broker pod:

[source,bash]
----
$ oc rsh broker-prod-ss-0
----

Inside the container shell, verify the JVM process status strings:

[source,bash]
----
sh-5.1$ ps aux | grep java
----

Your process listing command should explicitly display the appended Java Agent parameter pointing to port `9404`:
`... -javaagent:/amq/init/config/extra-libs/jmx_prometheus_javaagent.jar=9404:/amq/extra/secrets/jmx-metrics-config/config.yaml ...`

== Step 5: Test and Scrape Custom Telemetry Endpoints

From inside your cluster workspace, query the JMX Exporter metrics collection interface via its designated scraping port to check the output structure:

[source,bash]
----
sh-5.1$ curl localhost:9404/metrics
----

=== Expected Output Payload

Your metric rules output will return highly targeted entries resembling the structured block below:

[source,text]
----
# HELP artemis_address_size the number of estimated bytes being used by all the queue(s) bound to this address
# TYPE artemis_address_size gauge
artemis_address_size{_objectname="org.apache.activemq.artemis<broker=\"amq-broker\", component=addresses, address=\"samplequeue\"><>AddressSize"} 0.0

# HELP artemis_consumer_count number of consumers consuming messages from this queue
# TYPE artemis_consumer_count gauge
artemis_consumer_count{_objectname="org.apache.activemq.artemis<broker=\"amq-broker\", component=addresses, address=\"samplequeue\", subcomponent=queues, routing-type=\"anycast\", queue=\"samplequeue\"><>ConsumerCount"} 0.0
----

== Step 6: Eliminate JVM Runtime Metrics Remnants (The Scraper Whitelist)

Because the default Prometheus JMX Exporter client engine forces core system tracking metrics (`jvm_*` and `process_*`) into the output stream, configure an OpenShift `ServiceMonitor` wrapper to drop these metrics on arrival before they pollute your persistent dashboard databases.

Create a file named `broker-servicemonitor.yaml`:

[source,yaml]
----
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: amq-broker-jmx-monitor
  namespace: amq
  labels:
    release: prometheus-k8s
spec:
  selector:
    matchLabels:
      ActiveMQArtemis: broker-prod # Targets our primary custom resource deployments
  endpoints:
  - port: all-acceptor-0-svc-rte # Match your specific scraped service metrics target port
    path: /metrics
    interval: 30s
    metricRelabelings:
    # Intercept metric labels at ingestion layer
    - sourceLabels: [__name__]
      # A strict regular expression whitelist ensuring ONLY our high-value targets persist
      regex: '^artemis_(address_size|consumer_count|delivering_durable_message_count)$'
      action: keep
----

Deploy the monitor file to your operational project:

[source,bash]
----
$ oc apply -f broker-servicemonitor.yaml
----

Your OpenShift cluster monitoring engine will now securely collect, filter, and archive only your explicit metrics targets, maximizing both database performance and network efficiency.
